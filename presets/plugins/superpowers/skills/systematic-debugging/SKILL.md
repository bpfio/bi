# Systematic Debugging：系统化排查法

核心纪律：**先找根因，再动手修**。在定位到根因之前改任何代码都是赌博——
赢一次掩盖问题，输三次烧掉几小时。修复无根因的 Bug = 给系统埋更深的雷。

## 0. 进入条件

出现以下任一情况，立即进入本流程，并显式声明"进入系统化排查"：

- 报错、异常、崩溃、栈回溯
- 输出与预期不符（哪怕"看起来只是小偏差"）
- 测试失败、"之前是好的"、"我没改过这块"
- 别人报告的问题且无法立即看出原因

## 1. 四阶段流程（顺序不可跳换）

```
Phase 1 复现 ──► Phase 2 假设 ──► Phase 3 最小验证 ──► Phase 4 修复+回归
   ▲                  │                  │
   └── 复现不稳定? ────┴── 假设被证伪? ────┘（回到上一阶段，换假设）
```

### Phase 1：复现（Reproduce）——不能稳定复现的问题不能修

- [ ] 拿到完整错误现场：完整报错栈（不是最后一行）、输入、环境、时序
- [ ] 构造**最小稳定复现路径**：能用一条命令/一个脚本稳定触发的复现器（repro）
- [ ] 确定复现率：100% / 偶发 / 依赖时序。偶发问题先解决"可复现"再谈修复
- [ ] 记录环境三要素：版本（commit hash）、配置、数据状态

准出条件：有一个**可重复执行**的复现方法，且已存档（脚本/命令行记录）。

### Phase 2：假设（Hypothesize）——列出候选根因，按概率排序

- [ ] 读错误信息与栈，标出异常发生的**第一现场**（最早的异常点，不是最上层的报错）
- [ ] 列出 ≥2 个候选根因假设（只有一个假设=没思考，直接修第一个=赌博）
- [ ] 每个假设写清楚：**如果它为真，应该能观察到什么现象**
- [ ] 按可能性 × 验证成本排序，优先验证"便宜且区分度高"的假设

假设来源：栈回溯、日志时间线、最近变更（git log/diff）、数据流分析。

### Phase 3：最小验证（Minimal Verify）——每个假设用最小实验证伪

- [ ] 为排序第一的假设设计**最小验证实验**：加日志、打印中间值、
      二分输入、单独跑可疑模块——每次实验只回答一个问题
- [ ] 执行实验，记录观察值，与 Phase 2 的预测对照：
      - 观察 = 预测 → 假设增强，继续收窄或进入修复
      - 观察 ≠ 预测 → **假设被证伪，回到 Phase 2**，禁止硬拗
- [ ] 大空间用**二分定位**压缩搜索范围：
      - 代码时间维：`git bisect` 找引入 commit
      - 数据/流程维：注释掉后半段 / 打桩固定中间状态，看问题是否仍出现
      - 依赖维：逐层替换为桩（stub），看异常从哪一层开始
- [ ] 每轮实验后系统状态要能还原（实验代码用完即删，不混入修复）

准出条件：找到**能同时解释全部症状**的根因，且能指出具体代码行/配置项/数据记录。

### Phase 4：修复 + 回归（Fix & Regression）——修的是根因，不是症状

- [ ] 修复方案直指根因。修复前自问：**这个改动为什么能解决问题？**
      答不出来就还没到 Phase 4
- [ ] 禁止症状级补丁（如：吞掉异常、加 try-except 掩盖、改测试期望值迁就错误输出），
      除非显式标注豁免理由并留档
- [ ] 用 Phase 1 的复现器验证修复：跑一次必须失败的场景 → 修复后必须通过
- [ ] 跑全量回归（verification-before-completion L5），确认没修出新问题
- [ ] 检查同根因的**同类问题**还在哪里存在，一并处理或登记
- [ ] 留痕：根因描述 + 复现方法 + 修复 commit + 回归结果（排障手记格式）

## 2. 二分定位速查

| 场景 | 二分策略 |
|------|---------|
| 不知道哪个 commit 引入 | `git bisect start` + 好/坏端点，按提示逐轮 checkout 测试 |
| 长流程中某步产出坏了 | 在流程中间节点打印/落盘中间产物，确认坏在哪一段之前/之后 |
| 配置项怀疑 | 逐项恢复默认值，或逐项换成已知好值 |
| 大文件/大数据异常 | 对数据二分裁剪，找到仍触发异常的最小输入 |
| 并发/时序问题 | 先加全局串行化或强制延时使其稳定复现，定位后再移除探针 |

## 3. 检查清单（排障全程挂在手边）

- [ ] 我能稳定复现吗？（不能 → 先解决复现）
- [ ] 我现在改代码是为了验证假设，还是为了"碰运气修好"？（后者禁止）
- [ ] 我的假设被证伪了吗？（证伪 → 回 Phase 2，不许硬改）
- [ ] 我指出根因所在的具体代码行了吗？（指不出 → 还没完成定位）
- [ ] 修复后，原复现器跑过了吗？全量回归跑过了吗？
- [ ] 实验探针删干净了吗？
- [ ] 根因和修法写进手记/报告了吗？

## 4. 禁止行为（红线）

- **无证据乱改**：连续改多处代码看"哪个能好"——这是射箭不是排障
- **盲改竞速**：不等实验结果就连发多轮改动，各轮改动互相污染无法归因
- **修复即提交**：探索阶段的改动直接混进修复 commit，无法回溯假设链
- **症状修复**：报错被压下去但根因还在——下个季度它会带着更怪的面孔回来
- **跳过复现**："直接看代码找问题"只适用于一眼能看出根因的琐碎问题；
  5 分钟内定位不出，必须回到 Phase 1

## 5. 与其他技能的衔接

- Phase 4 完成后 → 回到 verification-before-completion 走完整验证清单
- 修复代码交付前 → subagent-driven-development 双阶段审查照常执行
- 需要隔离现场做实验 → using-git-worktrees（exp/ 分支）
