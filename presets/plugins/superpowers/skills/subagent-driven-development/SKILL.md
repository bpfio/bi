# Subagent-Driven Development：双阶段审查闭环

核心原则：**写的人不审自己的代码**。作者对代码有天然的确认偏差——他知道代码
"想做什么"，所以会不自觉地按"想做的"而不是"该做的"来读。因此审查必须由
独立角色执行，且分两道：一道查"做的是不是对的事"，一道查"做的事对不对"。

## 1. 角色与流水线

```
┌────────────┐   交付物    ┌───────────────┐   通过      ┌─────────────────┐   通过
│Implementer │ ─────────► │ Spec Reviewer │ ─────────► │ Quality Reviewer │ ─────► 宣布完成
│  实现者     │            │ 规格审查（对题）│            │ 质量审查（对味）   │
└────────────┘            └───────┬───────┘            └────────┬────────┘
      ▲  ╲ 拒绝                 拒绝│                          拒绝│
      │   ╲______________________│______________________________│
      │                          ▼                              ▼
      └──────────── 带具体修改指令返回 Implementer 返工 ◄─────────┘
```

三个角色可以由同一个执行体切换人格扮演，但**必须切换上下文独立执行**：
审查时只看交付物与规格，不看实现者的自述辩解。禁止"我写我审、一遍过"。

## 2. 阶段 0：Implementer（实现者）

- **输入**：任务规格（目标、DoD、约束、验收标准）
- **动作**：按需开隔离现场（using-git-worktrees）→ 实现 → 自跑
  verification-before-completion 清单 → 附证据提交审查
- **输出**：
  1. 代码变更（分支/工作区路径）
  2. 自验证据（编译/测试/lint/端到端输出）
  3. 实现说明（做了什么、没做什么、关键取舍、已知遗留）
- **准出条件**：交付物齐全 + 自验证据齐全。缺任一项，Spec Reviewer 直接退回

## 3. 阶段 1：Spec Reviewer（规格审查——做的是对的事）

- **准入条件**：收到完整交付物包（变更 + 自验证据 + 实现说明 + 任务规格）
- **审查清单**：
  - [ ] 是否逐条满足任务规格/DoD？有无漏做、多做、做偏？
  - [ ] 是否有超出规格的"顺手改动"？（有 → 要求拆出或说明理由）
  - [ ] 规格中的边界条件与约束（性能/安全/兼容性）是否被满足？
  - [ ] 自验证据是否覆盖规格声明的验收标准？证据是否针对最终代码？
  - [ ] 实现说明与实际变更是否一致（说了没做的有没有做，说了做的有没有做）？
- **输出**：结论 ∈ {通过, 退回} + 逐条意见（每条意见含：位置、问题、期望、严重级）
- **准出条件**：清单全过，无 P0/P1 级未决意见
- **退回格式**：指明规格条目号 + 不满足点 + 返工要求（可直接执行，不写"再改改"）

## 4. 阶段 2：Quality Reviewer（质量审查——做的事对不对）

- **准入条件**：Spec Reviewer 已通过（质量问题不救"做错的事"）
- **审查清单**：
  - [ ] 正确性：逻辑、边界、异常路径、并发/时序隐患
  - [ ] 可读性：命名、结构、注释是否解释"为什么"而非复述"做什么"
  - [ ] 一致性：是否遵循项目既有模式与风格（不是审查者个人偏好）
  - [ ] 健壮性：错误处理、资源释放、失败路径的行为
  - [ ] 安全性：输入校验、敏感信息泄露、权限边界
  - [ ] 债务：调试残留、硬编码、魔法数、应抽未抽的重复
  - [ ] 测试质量：测的是行为还是实现细节？断言有意义还是凑覆盖率？
- **输出**：结论 ∈ {通过, 退回} + 逐条意见（区分 P0 阻断 / P1 应修 / P2 建议）
- **准出条件**：无 P0/P1 未决项；P2 建议记录在案不阻断交付
- **退回格式**：同 Spec Reviewer，意见必须指向具体文件与行

## 5. 失败回退路径

| 场景 | 处置 |
|------|------|
| 任一阶段退回 | 意见原样返回 Implementer，**只修意见涉及项**，禁止夹带其他改动 |
| 返工后重新提交 | 从**退回的那个阶段**重新审起（前一阶段的通过结论仍有效） |
| 同一问题第 3 次退回仍未修对 | 升级处理：暂停流水线，重新对齐规格或换实现方案，禁止第 4 次盲试 |
| 两审查者结论冲突 | 以规格原文为最高仲裁；规格未覆盖处补写规格后再判 |
| 审查超时/审查者不可用 | 不得跳过审查交付；换审查上下文重跑或阻塞上报 |
| 紧急热修 | 允许"先修复后补审"，但补审必须在 24h 内完成并留痕，否则登记为欠账 |

## 6. 全闭环检查清单（宣布交付前）

- [ ] Implementer 交付物包齐全（变更 + 自验证据 + 实现说明）？
- [ ] Spec Reviewer 结论为"通过"且意见已归档？
- [ ] Quality Reviewer 结论为"通过"且意见已归档？
- [ ] 每次退回-返工的轮次与意见闭环有记录？
- [ ] P2 建议已登记（不阻断但不丢失）？
- [ ] 以上每一步都有留痕可回溯？

## 7. 反模式

- **自我审查**：实现者切个"心态"就当审过——上下文没换，偏差照在
- **审查即点赞**：Reviewer 只写"LGTM"没有逐条清单记录——等于没审
- **审查夹带返工**：返工时顺手重构别的，引入新偏差，审查白做
- **审查降级为格式检查**：只看缩进命名不看逻辑与规格符合度
- **流程绕行**："这次改动太小"——小改动审得快，但不是不审
