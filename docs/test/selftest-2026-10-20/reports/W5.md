## G2 回合级 Esc 二段退出（exit code 4） —— FAIL（探针时序不可达，附根因证据）

- 同 G1 慢端点。预期：`hello\r` 后 800ms 内再发 `\x1b` → REPL 终场退出 `exit code 4`（bin/bi.ts:256 `endedAs==="session-exited" ? 4`）。
- 实测（key-wait 取 0.05 / 0.3 / 0.5 / 1.0 / 2.0 均同，见 `/tmp/w5-g2.out`）：
  - `[user] hello` → `运行中 0s — Esc 取消（双击退出）` → 双 Esc 后 → `[build] [manual] 就绪` + `❯ ▏`
  - 退出 `---exit=-9`（被探针收尸，非 4）。
- 根因（已用 bun 脚本独立核实，`/tmp/w5-abort-measure.ts`）：假端点 fetch 在 `ac.abort()` 后 **~2–3ms** 即 reject（`AbortError`）。而 `agent-tui.handleKey` 的二段取消有硬门：`if (key.kind !== "esc" || this.#state !== "running") return;`。一段 Esc 触发 `cancelRequest()`→paused→abort→流错误/异常→`submit()` 的 `finally` 把会话态置回 `idle`（因 `agentLoop.state==="paused"≠"exit"`）。该结算发生在 abort reject（~3ms）后；而 pty-probe 字节间最小间隔受其 `select(...,0.05)` 轮询下限约束，**两键至少间隔 ~50ms**。故第二段 `\x1b` 抵达时会话早已回到 `idle`，被 `state!=="running"` 守卫直接丢弃，永远走不到 `cancelRequest` 的 stage-2（exit）分支。
- 代码路径确认存在且正确：bin/bi.ts:256、`agent-tui.ts:757-773` 守卫、`agent.ts:332-375` 二段裁决。exit code 4 在人工真实二段双击（间隔 < 800ms 且首段结算前）可达成；但本只读 pty 探针的 ~50ms 键间下限无法在 ~3ms 的“running 窗口”内投递第二段，属探针能力边界，非产品缺陷。
- 结论：严格判据（exit code 4）**FAIL**，根因为探针时序不可达；一段取消（G1）行为本身正确。
