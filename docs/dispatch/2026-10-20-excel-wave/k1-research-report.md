## 1. 核心结论（先看这十条）

1. 主循环的工程难点不在"调模型"，在**终止语义**：跑完没跑完、真失败、被打断、被拒绝——四种终态必须机器可读地分开。末帧契约是 CLI Agent 最重要的对外接口。
2. 流式三形态（text / json / stream-json）应当**共用一套内部事件流，只在序列化层分叉**，否则三套输出会各自漂移。
3. 上下文工程是"预算分配题"：系统提示、工具声明、对话历史、工具输出四者抢同一个 token 水位；压缩只压历史，截断只压单次大输出，两条管线不要混。
4. 装配顺序与优先级顺序是**两件事**：写入顺序通常内建基线→config→CLI→追加，同名字段后写入者胜；项目记忆必须落在系统提示区，不能塞进首条用户消息。
5. 工具输出截断的省略标记必须写明"省略了多少、如何读回"，否则模型会以为内容完整而基于残缺信息作答。
6. 只有 bash 的工具面等于把安全、审计、沙箱全丢给模型；read/write/edit/glob/grep 是不可省的稳定原语。
7. MCP 传输选择看**进程边界**：同机且要绑定生命周期用 stdio，跨机或集中鉴权用 HTTP 系（SSE／streamable HTTP 各版本规范并存，未核实版本与日期）；工具名必须带 server 命名空间。
8. 子代理的本质是**上下文隔离**：只交"目标 + 允许读路径 + 输出格式"，回传结构化结论，绝不把主代理历史整段搬过去。
9. 权限默认应当**默认拒绝**，并做到"每个鼠标/交互路径都有键盘等价物"式的可审计性；ask 提示必须写清动作、影响面、可撤销性，否则人只会一路回车批准。
10. 幻觉率只能用**行为证据**判定，不看回答文本；伪端点/假模型守得住代码路径覆盖，守不住真实服务语义变化；回归门禁要比基线趋势，不要卡绝对阈值。

## 2. 主题一：Agent 主循环设计

### 2.1 核心概念

- 主循环 = 模型调用 → 解析响应 → 执行工具 → 回填结果 → 再次喂回，直到显式终止条件成立。
- 单回合可携带**多个 tool_use 块**；批内调用的执行语义（并行/串行）是实现级选择，核心差别在状态管理与失败隔离复杂度。
- 终止条件分三类：模型主动结束、外部信号（用户中断、看门狗超时）、硬性回合上限。三类必须映射到**可区分**的终态。
- 循环需维护的运行态：消息列表、调用深度、累计 token/成本、当前激活工具集、已完成的副作用记录。

### 2.2 主流做法

- 批内调用默认视为**无数据依赖可并行**；多数 CLI 为简化状态选择严格串行。依赖关系交给模型——它必须等上一批结果回填后才发依赖调用，agent 不自动重规划。
- 并行分支只在满足三条时启用：调用间无数据依赖、工具幂等、结果顺序稳定可复现。
- 批内单点失败**隔离**：失败调用回填 error 结果块，不中断兄弟调用，由模型决定如何补偿。
- 回合上限耗尽时返回结构化终态而非抛异常，subtype 明确"未完成"原因。
- 嵌套 subagent 各自持有 turn budget，但 parent 累加计费——预算口径（是否共享、谁先耗尽）必须显式约定。
- 看门狗放在 agent 侧统一管理层，不分散在每个工具里。

### 2.3 常见坑与对策

| 坑 | 对策 |
|---|---|
| 把批内调用当严格顺序依赖，造成无谓串行延迟 | 依赖图交给模型，agent 只保证结果回填顺序 |
| 兄弟调用失败导致整批回滚，已完成上下文丢失 | 失败隔离，error block 同样进消息列表 |
| 回合耗尽被当运行异常抛出，CI 分不清"未完成"与"真出错" | 用独立 subtype 标注终止原因 |
| 循环异常退出无机器可读终态，消费方只能靠退出码猜 | 终态帧同时承载 subtype/is_error/usage |
| 父子代理预算口径不一导致预算失控 | 统一 parent/child 的 budget 继承与累加规则 |
| 超时后子进程留孤儿，长期运行后僵尸累积 | 看门狗统一收场：SIGTERM → 宽限期 → SIGKILL → waitpid 回收 |
| 超时被一律当作可重试 | 重试许可与工具幂等性绑定，非幂等工具超时不自动重试 |
| 管道消费吞掉退出码（`| tail` 之类） | 脚本侧显式 `set -o pipefail` 或读取终态帧而非退出码 |

### 2.4 代表实现怎么做

- Claude Code 风格末帧：`{"type":"result","subtype":"success"|...,"is_error":bool,"result":str,"session_id":str,"usage":{...}}`；具体 subtype 取值集合（未核实）。
- 退出码映射通行做法：成功 0；未完成/被拒/工具错误/内部错误分给不同非零码；自动化场景更应以"读到终态帧"为终止判据。
- 三形态共用内部事件流：事件层有 system / assistant / tool_use / tool_result / result 等，序列化层分 text（增量人读）、json（整块脚本）、stream-json（逐事件帧）。
- 结构化错误码通行分类：参数错（附 invalid_fields）、路径不存在（附 path）、权限拒绝（附 action/resource）、超时（timeout，标注是否可重试）、资源超限（rate_limit/quota，附 reset 提示）、内容冲突（content_conflict）、模型侧错误（model_error）。
- Codex CLI 与 Gemini CLI 亦提供机器可读的非交互输出开关（开关名与稳定程度未核实）；aider 基本是纯文本 + 会话历史文件，自动化侧能力最弱。

## 3. 主题二：上下文工程

### 3.1 核心概念

- 上下文窗口是**有限预算**，上下文工程 = 在预算内编排系统提示、工具声明、对话历史、工具输出、项目记忆。
- 三类可变内容：对话历史（持续增长）、工具输出（突发膨胀）、项目记忆（相对稳定）。
- **紧缩（compaction）与截断（truncation）是两条管线**：前者压历史，后者压单次大输出，混用会造成"摘要里混进被省略的日志"。
- 注入位置影响注意力：系统提示层 vs 首条用户消息层，顺序即优先级。

### 3.2 主流做法

- 触发水位通常设在窗口容量的 60%–80% 区间（各家阈值不同，未核实）；压缩策略 = 保留最近 N 轮原文 → 对早期轮做摘要 → 仍超预算则按 token 预算回退丢弃最旧。
- 摘要保"意图与决策"，丢细节；关键文件、硬约束以结构化要点保留，**压缩后强制把系统提示与行为准则重新置顶**。
- 工具输出超阈值（单输出约数千 token 量级，未核实）时：保留头尾 → 中间插明确省略标记 → 全量落盘并在结果里给出路径。
- 系统指令装配：内建基线 → config → CLI 参数 → 运行时追加；同名字段后写入者胜。项目记忆（AGENTS.md 类）在 config 与内建之间或紧邻 config 注入。
- 项目记忆按目录层级向上查找合并：仓库根 + 子目录多层，越靠近当前工作目录优先级越高；子层**追加**而非覆盖父层核心约束。

### 3.3 常见坑与对策

| 坑 | 对策 |
|---|---|
| 裁剪把系统约束一起压进摘要，导致模型"失忆" | 系统提示永远在压缩边界外，只压对话历史 |
| 省略标记写成 "…" 或 " [...]"，模型误判内容完整 | 标记写明省略行数/字节数 + 全量文件路径 + 读取方式 |
| 落盘后模型读不回来（路径没给或无权限） | tool_result 直接附可读路径与建议命令，而非只说"已截断" |
| 多层 AGENTS.md 简单拼接，重复指令放大 | 按层级合并去重，父层核心约束只保留一份 |
| 项目记忆塞进首条用户消息，优先级低于对话 | 注入系统提示区，位置在内建之后、运行时追加之前 |
| 工具声明排在任务之后，模型首轮选错工具 | 先系统提示、再工具声明、最后任务上下文 |
| 压缩把"待办"压没了，模型以为任务已完成 | 待办台账独立于对话历史保存，不进压缩管线 |

### 3.4 代表实现怎么做

- 项目记忆文件名因实现而异：Claude Code 用 CLAUDE.md（亦支持 AGENTS.md，未核实），Codex CLI 用 AGENTS.md，Gemini CLI 用 GEMINI.md（未核实是否同时读 AGENTS.md）。
- 记忆文件按当前目录向上查找合并，越近优先级越高；注入内容通常设软上限（数百到数千 token 量级，未核实），超出则告警或摘要。
- 全量卸载：工具输出写入项目内缓存/临时目录，tool_result 只含摘要 + 路径，后续用 read 类工具按路径取回。
- 压缩触发后一次性调用模型生成摘要替换旧轮次，保留最近若干轮原文，并在摘要首尾重申核心约束防漂移。

## 4. 主题三：工具面设计

### 4.1 核心概念

- 最小完备集 = read / write / edit / glob / grep / bash，外加"脚本执行"这一类长任务出口。
- read 解决"模型看不到磁盘"，write 解决从无到有产出，edit 解决最小改动（省 token、降低误改），glob 按文件名定位、grep 按内容定位（**两个检索维度不可互相替代**）。
- 不能只有 bash：裸 shell 让模型自拼命令、自解析输出，越权与幻觉风险高，且难以审计与沙箱化。
- edit 必须结构化：整文件写回（token 贵、易覆盖并发改动）/ 精确字符串替换 / search-replace 块（内容锚点、唯一匹配校验、抗行号漂移）。
- MCP 是以标准协议接入外部能力的扩展面；子代理的核心是上下文隔离；权限三态 allow/deny/ask 是副作用的守门员。

### 4.2 主流做法

- 高频动作专用化：read/edit 优先于 bash，只有真正需要 shell 才走 bash。
- MCP stdio：server 作本地子进程随客户端拉起，生命周期绑定、无额外鉴权、日志可见，适合同机。
- MCP SSE / streamable HTTP：server 独立部署，可跨机器、集中鉴权与限流，代价是连接管理与认证过期风险，调试需看服务端日志。两种 HTTP 形态在规范中并存情况未核实。
- MCP 发现靠配置声明（命令/URL/环境变量），客户端启动时拉起或连接；工具名统一加 server 命名空间前缀避免冲突。
- MCP server 崩溃应**降级不崩轮**：工具暂时不可用并标注，恢复后重连。
- 子代理派发三要素：目标 + 允许读取的路径 + 输出格式约定；子代理工具白名单通常比主代理更窄（只读 + 搜索），写与 bash 留在主代理，形成权限分级。
- 权限默认取向：关键操作 ask、读类可放行；但更稳妥的设计是默认拒绝 + 显式放行清单。

### 4.3 常见坑与对策

| 坑 | 对策 |
|---|---|
| edit 用行号定位，文件被改后错位 | 内容锚点 + 上下文窗口 + 唯一匹配校验，匹配不唯一直接失败 |
| 只有 bash，模型拼出危险命令 | 原语专用化 + bash 之上叠权限层 + 危险组合显式 deny |
| stdio 型 MCP server 卡死拖垮主进程 | 独立进程隔离 + 超时 + 崩溃即降级 |
| 远端 MCP 认证过期且无提示 | 连接健康检查 + 明确错误回传，要求用户重连 |
| 子代理误带主代理全量历史撑爆窗口 | 严格只传目标与允许路径，历史一概不传 |
| 子代理回传自由长文本污染主上下文 | 约定结构化结论（结果 / 依据 / 未解决项） |
| ask 提示太简略，人随手"全部允许" | 提示写明"将执行什么、影响哪些文件、能否撤销" |
| 权限规则只匹配命令名，漏掉危险参数 | 支持前缀 + 参数级规则，危险组合显式 deny |

### 4.4 代表实现怎么做

- Claude Code：内置 read/write/edit/glob/grep/bash，edit 要求唯一匹配；MCP 原生集成；子代理（Task）为独立派发单位；权限规则落在 settings 类配置文件。
- Codex CLI：shell 与命令执行受沙箱与审批模式双重约束（具体档位名未核实），工具面以命令执行为主。
- aider：无独立 glob/grep 工具，检索交给 bash；核心是 search/replace 编辑块 + repo map；扩展靠脚本而非 MCP。
- 通用规律：写与网络操作默认需确认；MCP 工具纳入同一命名空间并参与权限判定。

## 5. 主题四：会话与持久化

### 5.1 核心概念

- 会话恢复 = 把一轮对话（消息 + 工具调用 + 轻量环境）落盘，使"状态可重建"；checkpoint = 在关键节点快照，从最近一致点续跑。
- 存什么：用户/助手消息、工具调用及结果、工作目录等轻量环境、待办台账。存哪：本地项目隐藏目录或用户级 cache，JSONL 是主流格式（便于增量追加与损坏容忍）。
- 幂等：恢复后**不重放已完成副作用**，以持久化的结果记录为准，而不是重跑工具。
- 台账（todo）：条目 + 状态 + 依赖，模型与宿主共享同一真相；后台/cron 任务把延时动作从主会话剥离。

### 5.2 主流做法

- append-only 消息流，恢复即重放重建上下文（早期消息做摘要压缩）。
- 恢复前做"副作用对账"：依据已记录的 tool_result 判断哪些改动已落盘。
- 台账结构常见为 `{id, 内容, 状态(open/in_progress/done), 依赖[]}`，模型写、宿主渲染与持久化。
- 台账与真实文件系统对账：用 glob/grep 验证产物存在，卡住时标阻塞而非假完成。
- cron 持久化在本地调度文件，主会话退出后仍由守护侧定时检查触发；记录 last_run 以便补跑。
- 多会话用目录前缀或 worktree 隔离工作树，避免两个任务互相覆盖。

### 5.3 常见坑与对策

| 坑 | 对策 |
|---|---|
| 会话文件写一半崩溃导致截断 | 原子写（临时文件 + rename），恢复时丢弃不完整的最后一条 |
| 恢复后重放 bash，造成重复副作用 | 以持久化结果为准，恢复不自动重放工具调用 |
| 台账说 done、实际没做 | 关键完成必须有工具结果或文件证据佐证 |
| cron 错过触发（机器休眠） | 记录 last_run，"错过即下次补跑" |
| 多会话共用目录互相覆盖 | 会话级 worktree/沙箱，或串行占用同一目录 |
| 重放过长撑爆上下文窗口 | 恢复时对早期消息摘要压缩 |
| 后台任务与主会话共享上下文致混乱 | 后台只回传结构化结论，不污染主上下文 |
| 后台任务失败无限重试造成雪崩 | 有限重试 + 状态回写 + 一次性告警 |

### 5.4 代表实现怎么做

- Claude Code：会话以本地 JSONL 转录保存，支持恢复历史会话（具体路径未核实），恢复时重建消息流并压缩早期历史。
- Codex CLI：以本地 rollout 日志保存会话并支持回放/恢复（路径与格式未核实）。
- aider：以聊天历史文件落盘可续聊，配合 git 做检查点与撤销，无显式 cron/后台体系。
- Gemini CLI：本地会话历史与恢复能力具备（路径与成熟度未核实）。
- 通用规律：后台/定时能力多由宿主侧或插件侧实现，核心 CLI 只保证"退出不丢会话"。

## 6. 主题五：评测与质量保障

### 6.1 核心概念

- 幻觉率两种测法：直接问答（问模型"你是否编造"）与错误率自报，**都依赖回答文本，偏差大**；行为学探针则构造场景，以 agent 实际调用的工具、写入的文件为证据。
- 覆盖度测试的目标是"用接近零成本验证所有代码路径都被触发过"，不是验证输出正确性。
- dogfood 自食是质量信号，也是偏差来源；回归门禁是把评测结果变成合入/发布阻断条件。
- 评测的核心张力：真实感与可控性通常互斥，须分层折中。

### 6.2 主流做法

- 探针设计四式：诱导性提问（埋陷阱让模型顺着错）、错误前提（"用 v3 的 API 改这段代码"）、不可知问题（"这个内部函数谁写的"）、来源引用要求；再加"执行后验证"（跑测试/读文件后再答）与"不知道就说不知道"。
- 判定标准：回答声称成功但无对应副作用（无文件改动、无工具调用、无请求）即判幻觉。
- 伪端点守护：本地起 stub HTTP 服务返回录制响应，让 agent 在无真实账号/额度下跑完整流程。
- 录制回放（首跑录 request/response，后续重放）与契约测试（断言请求形状）分工。
- dogfood 前提：产品自身够稳、团队真有真实任务可做、建立"踩坑即报 bug"的闭环。
- 门禁分层：快门禁（单测/类型检查/确定性探针，每次提交跑）与慢门禁（全量对话评测 + 人工抽检，定时或合并前跑）。
- 抖动容忍：对同一任务跑多次做配对比较、与历史基线比趋势而非绝对阈值、偶发失败自动重试。

### 6.3 常见坑与对策

| 坑 | 对策 |
|---|---|
| 直接问答测法偏差（过度否认或过度自信） | 只认行为证据，文本自报不计入 |
| 探针被"教聪明"，agent 见过同类题后学会套路 | 定期换题、保留私有/未公开探针集 |
| 录制过期后回放仍绿，真实 API 已变 | 定期刷新录制，录制时效纳入门禁 |
| 契约测试形状对但语义错 | 少量真实端到端与之混用 |
| 自食退化：开发者知道内部捷径，只走自己想得到的路径 | 保留原始会话日志 + 引入外部用户路径 |
| 新手盲区覆盖不足（开发者不会像新手那样乱用） | 单独维护"新手视角"评测集 |
| 门禁抖动误报，采样噪声导致偶红 | 重试 + 基线趋势对比，不卡绝对阈值 |
| 时间戳、并发顺序、文件系统遍历顺序引入不确定性 | 冻结时间、固定种子、隔离文件系统 |

### 6.4 代表实现怎么做

- 探针常以"埋雷对话集"存在：每条预设期望证据（应调用某工具 / 应写入某文件），跑完自动核对。
- 假模型守护：本地起一个返回固定 JSON 的 LLM 代理，或用录制脚本替换 provider，使评测零 API 成本。
- 自食落地：团队日常 PR 由自家 agent 生成，踩坑进 issue，形成"自用即测试"闭环。
- 门禁红了先查快层（确定性失败=代码真坏），再查慢层（可能是采样抖动）。

## 7. 主题六：交互体验

### 7.1 核心概念

- TUI 是日常主界面，核心矛盾是信息密度与可读性；diff 渲染是建立信任的关键。
- 交互必须同时服务鼠标用户与纯键盘用户，**两者要有等价路径**。
- slash 命令（人触发）与工具调用（agent 触发）边界必须清晰。
- headless 的关键不是没有 TUI，而是**稳定的输入输出契约与退出码语义**。
- 流式渲染要求边生成边画且不闪烁；可视化面板的定位是"让人看懂 agent 干了什么"，不是再造控制台。

### 7.2 主流做法

- diff：逐行（unified）与并排（split）可切换；用语义色区分增/删/改，而非仅红绿。
- 着色降级：检测真彩支持，退回 16 色或改用 `+ / − / ~` 前缀符号保可读性。
- 鼠标：滚轮滚动历史、拖选复制、点击定位；键盘侧提供方向键/PgUp/跳转标记等价物。
- slash 命令：动词化命名（/review、/compact）、输入 `/` 弹出补全、完成选择后转为一条结构化用户消息进入同一对话循环。
- 输入框：多行支持、粘贴大段文本不触发提交、引号括号自动配对与智能缩进。
- 宽窄自适应：按 COLUMNS 动态折行；并排 diff 在窄屏自动退化为逐行。
- 流式重绘：增量更新（只重画变化行）+ 双缓冲，避免整屏清屏。
- headless 输出格式由参数或管道环境选择；退出码按类别细分（成功/使用错误/运行错误/被拒），不全部退化为 1。

### 7.3 常见坑与对策

| 坑 | 对策 |
|---|---|
| diff 只有红绿，看不出语义 | 加语义色 + 可配上下文行数 + 关键改动高亮 |
| 鼠标路径无键盘等价，排斥终端与无障碍用户 | 每个鼠标操作都要有键位 |
| slash 命令与工具调用混淆（以为 /xxx 不走推理） | 明确边界与提示语，命令内部仍可走 agent 循环 |
| 粘贴大段文本误提交 | 粘贴期间临时禁用自动提交，或要求显式发送键 |
| 流式输出整屏重绘导致闪烁 | 原地更新 + 节流 + 只重画变化区域 |
| headless 下卡在确认提示 | 非交互模式强制非交互策略（自动拒绝或显式开关），不挂起等待 |
| 退出码全用 1，脚本无法分支 | 细分退出码语义并写进文档 |
| 面板做成控制台，堆满按钮反而更难懂 | 聚焦回放 + 审阅 + 成本三件事 |

### 7.4 代表实现怎么做

- TUI 多用终端原始控制（alternate screen + 光标定位）实现 diff 与流式重绘，宽窄靠环境变量探测。
- headless 模式识别非 TTY（stdin 非终端 / 显式 print 开关）即切 json 或 text，遇需确认读标志位决定而不等待输入。
- 可视化面板多从会话日志（JSONL）读事件重建时间线、diff 与成本，不必自建状态存储。

## 8. 代表实现对照

### 8.1 Claude Code

- **最值得借鉴**：项目记忆文件 + 权限规则文件 + 机器可读 headless 三件套齐全；子代理（Task）为独立派发单位，可并行、可自定义。
- **最该避开**：接近上下文上限时自动压缩可能丢掉早期约定，长会话需手动 `/compact` 兜底；默认权限偏宽松，需显式收紧。
- **最独特机制**：slash 命令、子代理定义文件、headless 自动化接口三者互相咬合，组成"同一套会话、两种消费方式"。
- 上下文策略：接近上限触发自动摘要压缩（阈值未核实），另有手动压缩命令；会话以本地 JSONL 转录保存并可恢复（路径未核实）。

### 8.2 OpenAI Codex CLI

- **最值得借鉴**：**审批档位 + 沙箱执行**双层约束——用机制兜底而非只靠弹窗，这是与"确认制"路线最本质的分野。
- **最该避开**：全自动档位下执行任意命令风险高；沙箱档位配置复杂，配错等于没沙箱（具体沙箱实现随平台不同，未核实）。
- **最独特机制**：以"补丁"为核心交付物，shell 在受限环境执行。
- 上下文策略：依赖模型侧自动压缩，触发逻辑未核实；会话以本地 rollout 日志保存并可回放（路径未核实）。

### 8.3 aider

- **最值得借鉴**：search/replace 块编辑格式 + repo map（用语法分析把仓库结构与符号摘要喂给模型），是"用少量 token 表达大仓库"的经典解法。
- **最该避开**：强依赖 git 仓库与提交作为检查点，脱离 git 体验显著变差；块格式写错需重试，成本高。
- **最独特机制**：git diff 作为变更真相源，配套自动 lint/测试钩子形成闭环。
- 上下文策略：靠 repo map 压缩仓库规模（map token 上限可配），**对话历史不自动压缩**，靠用户管理；权限取向最激进——默认直接编辑并自动提交（可关闭），靠 git 可回滚兜底。

### 8.4 OpenCode

- **最值得借鉴**：provider 无关架构——统一 provider 接口接任意模型后端，更换后端不改上层。
- **最该避开**：项目较新，生态与稳定性弱于成熟工具；配置项多，学习成本高。
- **最独特机制**：LSP 集成 + 以 session 为中心的 TUI/守护式架构。
- 上下文策略：基于 token 预算自动压缩/截断（细节未核实）；会话本地 JSONL 可恢复并有 session 列表；MCP 与 plugin 结合；权限默认对危险命令确认（具体默认未核实）。

### 8.5 Gemini CLI

- **最值得借鉴**：extension 作为一等分发单元（可打包 tools/commands/认证），比散装配置更可运营。
- **最该避开**：绑定 Google 账号/密钥与配额，存在网络与隐私顾虑；工具生态较新。
- **最独特机制**：超大上下文窗口天然缓解压缩压力，因此弱化了压缩机制（窗口大小随版本变化，未核实）。
- 上下文策略：因窗口大而默认不激进压缩（细节未核实）；自定义命令 + MCP 原生支持，配置思路与 Claude 的 mcp servers 格式相近（兼容性细节未核实）。

### 8.6 补充实现

- **Goose**：以 MCP/扩展为一等公民的本地 agent 引擎，支持本地模型，声明式 recipe 编排多步任务——借鉴点是把"能力供给"完全插件化；坑是代码编辑专项体验不如专用工具。
- **Cline**：plan/act 双模式 + 逐条 diff 审批 + MCP 市场；借鉴点是"每一步都可批"的信任设计；坑是重度绑定 IDE，CLI 形态与自动化接口最弱。

### 8.7 横向对照

| 实现 | 默认权限取向 | 上下文压缩 | 自动化接口 |
|---|---|---|---|
| Claude Code | 确认制 + 可配 allow/deny | 自动摘要（阈值未核实） | headless/print，较成熟 |
| Codex CLI | 审批档位 + 沙箱兜底 | 模型侧自动压缩（未核实） | 批处理较强 |
| aider | 默认允许（自动提交） | 不自动压缩对话，靠 repo map | 弱（文本输出 + 历史文件） |
| OpenCode | 危险命令确认 | token 预算自动截断（未核实） | 中等 |
| Gemini CLI | 确认制 + 可配 auto-accept | 因窗口大而弱化 | 有 JSON 输出（开关名未核实） |
| Goose / Cline | 确认制 / 默认拒绝 | 未核实 | CLI 形态弱 |

跨实现观察：

- **权限两派**：确认制（Claude Code / Gemini CLI / Goose / Cline）与"机制兜底派"（Codex CLI 沙箱、aider 靠 git 回滚）——后者把安全交给机制而非人的每次点击。
- **真正的隔离只有沙箱**：多数实现以"确认弹窗"替代隔离，安全模型与 Codex 的沙箱执行本质不同。
- **子代理是一等公民与否是分水岭**：Claude Code 的 Task 子代理体系最成熟，其余多为单代理循环或早期多代理实验（成熟度未核实）。
- **MCP 已成事实标准**：多数主流实现原生支持，aider 最弱（MCP 非其核心路线）。
- **项目级持久指令缺统一抽象**：Claude Code 的 CLAUDE.md 与 Codex 的 AGENTS.md 正在收敛出跨工具约定，其余实现各用 settings 风格配置。
